# User Taste
- Keep underlying data intact; suppress duplicate entries at the UI/presentation layer rather than removing them from the data model. Confidence: 0.7
- Do not rename source worksheet names in timekeeping/billing files; preserve the original worksheet name to avoid replacing scan identifiers and creating duplicate employee entries. Confidence: 0.8
- Present distinct data categories (e.g., absences vs. undertime) as separate UI sections rather than combining them. Confidence: 0.8
- Expects data exported to external/source systems to align exactly with the system's documented column order and structure. Confidence: 0.8
- When exporting row data, do not overwrite columns whose headers contain "total" (formula-only columns). Confidence: 0.8
- Do not overwrite columns whose values are already supplied by the source/template (e.g., "pay type"), whether or not the header contains "total". Confidence: 0.8
- Column mapping and formula-index protection should be service-specific (e.g., janitorial vs. operations vs. manpower timekeeping tables). Confidence: 0.7
- Include a timestamp in generated filenames to prevent name collisions when regenerating files for the same period. Confidence: 0.9
- Exclude rest days from regular-hour auto-input calculations; operations rest day varies per employee per month, janitorial rest day is Sunday, and manpower rest days are Saturday and Sunday. Overtime should still be counted on rest days. Rest days are excluded from auto-*input* only — hours a user explicitly enters on a rest day must still count toward the billed total. Confidence: 0.9
- Time inputs for DOF timekeeping (undertime, overtime, night differential, janitorial rendered hours) should use an `hh:mm` format, not `hh:mm:ss`. Confidence: 0.9
- For complex or evolving business rules (e.g., per-employee rest-day schedules), prefers discussing implementation options/ideas before committing to a specific approach. Confidence: 0.6
- Prefers per-employee override controls in wizards for employee-specific scheduling rules (e.g., rest days), rather than global or per-month configuration. Confidence: 0.9
- DOF timekeeping tables are structured as 16 rows per employee, one row per day; entries (hours, absences, UT/OT/ND) must be written to the row matching their date, and rows falling outside the selected billing period must be left blank. Confidence: 0.8
- Wants full per-day visibility in the UI: display all day rows for each (deduplicated) employee so date/row misplacements can be spotted before saving. Confidence: 0.7
- In Angular templates, prefers the built-in control flow blocks (e.g., `@for`) for rendering lists. Confidence: 0.6
- When reporting a bug, pastes the full raw error output (error objects, stack traces, request IDs, HTTP logs) with minimal prose, or describes only the expected output ("it should input how much the total UT/OT/ND per employee in each sheet"); expects root-cause diagnosis and a fix rather than clarifying questions. Confidence: 0.75
- For bugs involving generated/exported output, wants the diagnosis grounded in the real artifacts — dumping actual headers, formulas, number formats and row values from the live template and real generated files — rather than inferred from reading the code. Chose verification against the source of truth over acting on an unverified hypothesis. Confidence: 0.75
- When a verified finding disproves an earlier hypothesis, expects to be told plainly and for the plan to be dropped or rewritten rather than pursued anyway; accepts losing a planned large refactor when the bug turns out not to exist. Confidence: 0.7
- When records cannot be matched to a destination row in a generated file, prefers warn-but-save with a flagged marker row (e.g. `UNMATCHED`-prefixed) plus a visible list over blocking the save — user-entered data must never be silently dropped, and the unmatched state must stay actionable after the step advances. Confidence: 0.75
- Answers short multiple-choice scoping questions once facts have been verified against real data; the "no clarifying questions" expectation applies to unverified guesswork, not to scoped options backed by evidence. Will accept several such questions in one round and usually takes the recommendation — but will pick an "I'll inspect it myself" option over a recommended speculative change when the change touches live billed output and the artifact (e.g. the SharePoint-hosted template) is one the assistant cannot open. Confidence: 0.72
- Prefers fixing every real gap discovered during verification rather than restricting to the originally reported symptom — both domain gaps (unmapped night-differential or excess-OT columns) and collateral ones such as pre-existing unrelated test failures the assistant flags as out of scope; wants the whole suite green, not just the reported case. Confidence: 0.65
- Resumes interrupted work with a bare "continue working on the last prompt" or "retry doing the last prompt" (including after a provider/tool error), with no additional context; expects the assistant to reconstruct the in-progress task state itself (e.g., from saved plan documents and the current codebase) rather than asking what the prior task was. Confidence: 0.7
- In generated DOF billing files, the {billingPeriod} placeholder must render as `for the period {MONTH} {twoDigitDayRange}, {fullYear}` — e.g., "for the period SEPTEMBER 01-15, 2026" (uppercase full month name, zero-padded day range, four-digit year). Confidence: 0.9
- When requesting text/format changes, states the exact target output as a literal template string with named placeholders (e.g., "for the period {MONTH} {twoDigitBillingPeriod}, {fullYear}"); implement the format literally, including casing and zero-padding. Confidence: 0.6
- Makes requests as terse one-liners describing only the desired end behaviour — feature asks (e.g., "the user should also indicate their handled clients before signing up") and fix directives alike (e.g., "fix the app.spec.ts failure") — with no implementation spec; expects the assistant to work out and implement the full-stack changes (frontend form, backend validation/controller) or repair the broken test, without clarifying questions. Confidence: 0.65
- When writing values to generated spreadsheet cells, a format-conversion (e.g. decimal hours → Excel day-fraction by /24) must be applied only to cells whose number format expects it; never blanket-apply a value conversion across related columns even if they are sibling fields. Per the latest directive, billing hours-rendered (NO. OF HOURS RENDERED), OT *and* ND totals must all render as `hh:mm` — written as day-fractions (hours/24) into the template's `[hh]:mm`-formatted columns — while UT and absent columns keep plain decimal hours (the JAN undertime column is a template formula yielding minutes, a plain number; UT's format was not confirmed, so it was left unconverted and flagged). The template's Daily-Rate/Undertime formulas (`=ROUNDUP(G8/8*24,0)`, `=((G8/8*24)-(F8))*8*60`) were designed for the hours cell to hold a time value, so decimal hours made them compute garbage (e.g. a `-120` undertime). Since the backend never sets number formats, each column's actual format must still be confirmed in the live template before writing. Confidence: 0.9
- Introducing or changing an input UI must not destroy data already present in the source: existing values must be hydrated into the new view on load, and edits must not delete or collapse pre-existing records. Partial/typed-in-progress input must not overwrite a stored value; clearing should require an explicit deliberate action. Confidence: 0.8
- When a change to generated output is made, wants it locked in by a targeted regression test that drives the real component, and a note distinguishing new failures from pre-existing unrelated test failures. Where a codebase has no test runner (e.g. a plain backend utils file), accepts a standalone scratch script that re-declares the pure function verbatim and exercises it exhaustively — the script must stay a faithful copy of the shipped code, since a drifted copy tests nothing. Confidence: 0.75
- When a wrong value in generated output traces to the template's own Excel formula rather than to app code, prefers fixing the formula in the template and passing the exact value through unchanged — rejects code-side compensation (e.g. snapping/rounding totals) that silently alters billed hours. Expects the diagnosis plus the replacement formula as the deliverable, and a clean revert of any compensating code already written. Confidence: 0.8
- Expects the assistant to flag when a formula fix changes the *meaning* of a billed column (e.g. rounding artifact → actual unpaid time), so it can be confirmed with the business owner before shipping. Confidence: 0.7
- Optimization requests come with an explicit non-regression constraint ("improve X without breaking its functionality"). Prefers transport/throughput-level changes that leave read and write semantics byte-identical, and treats any change to *what gets written* (e.g. diff-only/change-only writes) as separate, riskier work to be scoped on its own rather than folded in. Once scoped separately, approves it behind an opt-in feature flag that defaults to off, keeping the original write-everything path intact and reachable so the two can be A/B'd on a real billing period and proven cell-for-cell identical before the new path is trusted. Confidence: 0.85
- When a cheaper optimization is available but rests on a stale or unverified source of truth (e.g. diffing against a client-side snapshot captured at load time, which does not know about a partially-failed prior save), expects the assistant to reject the cheap version and pay the extra read to compare against live server state — and to say plainly why the fast path is unsafe. Rationale given: a false "unchanged" silently keeps the wrong value in the file, while a false "changed" only costs one redundant write. Confidence: 0.8
- Data-integrity guard rails to expect in any write-skipping/dedup/caching logic: a missing or unprovable record must be written, never treated as unchanged; if the baseline read fails, fall back to the full write rather than diffing against a partial map; append/`rows/add` paths are never skipped; and formula-protected or computed fields are excluded from the comparison, not just the write. Confidence: 0.8
- For risky write-semantics changes, expects the new path to be made observable from the start — written-vs-skipped counts in the summary log plus a field in the response — so a suspiciously low skip count can be read as "the optimization is inert" rather than "it worked". Confidence: 0.75
- For non-UI technical work (performance, architecture), opens with "how would i do it?" and expects a diagnosis plus scoped options with concrete trade-offs before any code is written — the same approach-first expectation as for UI decisions, not a jump straight to implementation. Confidence: 0.75
- Expects performance work to be grounded in measured evidence from real artifacts (actual request durations and error codes from logs, config constants, real batch shapes) rather than assumptions about where the bottleneck is; stating "the frontend is not the problem" with quoted log evidence is the expected deliverable. Confidence: 0.7
- When verifying a performance/optimization change, wants proof of output equivalence — a cell-by-cell diff of the real generated artifacts against the pre-change output — not just a faster run. A change that is faster but writes different values is a regression regardless of timing, and the assistant should say plainly which verification steps it could not perform (e.g. needing the live tenant). Confidence: 0.75
- Prefers a performance change kept to a single identified hot path, with adjacent opportunities (other slow flows, setup/create steps) explicitly listed as out of scope rather than bundled into the same change. Confidence: 0.65
- Against rate-limited/throttled external APIs, prefers conservative adaptive concurrency with real backpressure over aggressive parallelism — speed must not come at the cost of more errors, so a slower run with fewer 500s counts as the better outcome. Chose a full return to the serialized version (128s) over a middle-ground low-concurrency variant when the adaptive-parallel version regressed to 2573s with 68 throttles and a failed save. Confidence: 0.7
- Expects the assistant to flag security problems found incidentally while doing unrelated work (e.g. a hardcoded cloud API secret committed in a repo script), with a rotate-and-move-to-env recommendation, surfaced separately from the main task. Expects the flag to be repeated on later tasks until it is acted on. Confidence: 0.65
- Expects the assistant to flag the aftermath of a failed/partial run (e.g. a save that committed rows for an hour before throwing may have left partial writes) as an actionable next step before retrying, so retries don't stack duplicates or build on half-written state. Confidence: 0.7
- Values honesty about self-inflicted error and its blast radius: when a change makes things worse, wants the assistant to name it plainly, quantify it against the previous baseline (before/after table), apologize without excessive hedging, and then revert to the known-good version rather than patching forward. Does not want the failure minimized or reframed as a partial success. Confidence: 0.8
- For value-comparison logic over persisted data, expects the assistant to enumerate the specific failure modes each rule addresses (float representation drift, blank-vs-null equivalence, numeric strings, leading zeros, trailing padding, NaN) rather than writing a generic equality check. Coercions must be lossless — e.g. `'007'` must not compare equal to `7` — because identifiers carry leading zeros and a false match silently skips a real write. Confidence: 0.8
- In the generated DOF billing file, NO. OF HOURS RENDERED (JAN/OMS/MAN worksheets) must be the sum of the regular hours from the matching timekeeping sheet, and the OT and ND columns must be the sums of the specified OT/ND entries — all three rendered as `hh:mm` (user confirmed explicitly: "the format is [hh]:mm" and "the no. of hours rendered should be hh:mm"). Stated verbatim four times when the output was "still not right" — treat as the acceptance criterion for billing totals. Confidence: 0.9
- Frontend test stack is Vitest with globals (`describe`/`it`/`expect`/`vi`) run via `npx ng test`; Jasmine/Karma APIs (e.g. `jasmine.createSpy`) do not compile in this project. Confidence: 0.9
- There is no shared test-setup file; jsdom lacks `window.matchMedia` (read by ngx-sonner while rendering), so polyfill it locally in the spec's `beforeAll` rather than adding a global setup file other suites would inherit. Confidence: 0.85
- When a required artifact cannot be opened by the assistant (e.g. DOF-BILLING-TEMPLATE.xlsm lives only in SharePoint), prefers to inspect it personally and confirm the specifics (column number formats) before any format-dependent change; the assistant should ask targeted questions and wait for the confirmation rather than write speculative values that may render as dates. Confirmed in practice: after being asked, inspected the template and answered with the exact formats ("the format is [hh]:mm", "the no. of hours rendered should be hh:mm"). Confidence: 0.78
- When saved data's period differs from the generated file's period, prefers regenerating only the minimal affected artifact (a new billing workbook) and leaving the rest of the setup (timekeeping files) untouched — minimal blast radius over a full re-setup. Confidence: 0.65
- Prefers idempotent artifact resolution on regeneration across DOF artifacts: when a file for the target billing period already exists (DOF-BILLING drafts and DOF timekeeping files alike), load that file with its existing data and update it in place; generate a new file only when none exists for the period — the stated goal is that generating the same period twice never creates duplicates. Confidence: 0.8
